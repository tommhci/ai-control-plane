# Route-Based Continuous Execution

Status: reusable control-plane policy.

Companion to `pre-task-decision-flow.md` (what is authorized before the task
starts) and `failure-recovery-flow.md` (what to do when something fails during
execution). This protocol governs **how far an AI may advance without stopping
for user input once a route has been authorized**.

The goal is to convert repeated per-step user approvals into one bounded route
authorization, so the user is consulted only on genuine decision points and hard
stops, not on mechanical progress within an already-approved scope.

---

## 1. Route Authorization

A **route** is a bounded unit of work authorized by the user in a single
instruction. It replaces repeated per-step confirmations inside that boundary.

Before the first action, the AI must declare the route. A valid route
declaration includes all of the following fields:

| Field | Required content |
|-------|-----------------|
| `route_name` | Short label (e.g. `fix-variable-flag`) |
| `allowed_repos` | List of repo roots; all others are forbidden |
| `allowed_files` | Explicit file list or file class (e.g. `src/features/**`) |
| `allowed_phases` | e.g. `read`, `edit`, `commit`, `test` |
| `validation_commands` | One or more commands that must all pass before each commit |
| `commit_policy` | When the AI may commit (see section 3) |
| `continuation_policy` | When the AI may advance to the next task (section 2) |
| `forbidden_actions` | Explicit list (e.g. `push`, `governance edit`) |
| `hard_stop_conditions` | Binary list; any match halts execution (section 4) |

A route that does not declare all fields is not a valid route. The AI must treat
it as a single-step STEP-mode task until the user fills in the missing fields.

**Route authorization is pre-task, not mid-task.** The AI may not self-extend a
route to cover additional files or repos discovered during execution. If
additional scope is needed, stop and ask.

**A route does not override permissions, hooks, or deny rules.** Platform-level
permission prompts, pre-commit hooks, and explicitly configured deny rules remain
in effect for the full duration of the route. If a hook blocks an action that the
route authorizes, resolve the hook correctly, do not suppress it. The route is an
AI behavioral contract; hooks are a system enforcement layer that the route cannot
override.

---

## 2. Continue Without Asking

The AI may advance to the next task inside the route without pausing for user
confirmation when **all** of the following are true:

1. The next action falls within the declared route scope (allowed repos, files,
   phases).
2. The diff touches only declared files; no undeclared file has been staged.
3. Validation passed (or a documented no-test reason is recorded in session
   output).
4. The commit message is factual and scoped to the current change.
5. If a task is blocked: at least one independent route task remains and the
   blockage is recorded as `[SKIPPED: <reason>]`.

If any condition is false, stop and surface the specific failure to the user.

---

## 3. Auto-Commit

The AI may commit without asking when **all** of the following are true:

1. The diff is fully contained within the declared file list.
2. The validation command exited 0 (or the no-test reason is documented).
3. The commit message is factual (describes what changed, not why it was
   authorized).
4. No unrelated dirty files are staged; unrelated changes are excluded from
   the index (e.g. via `git add <specific-files>` rather than `git add .`).
   Do not silently stash unrelated changes - if the worktree has unrelated
   dirty files, exclude them explicitly or hard-stop and surface them.
5. Governance, product, and control-plane changes are committed as separate
   commits, never mixed in one commit.

A commit that violates any of the above requires user confirmation.

---

## 4. Governance Token Retry

Some projects use a pre-commit hook that blocks commits to protected governance
paths unless a valid token file was generated by a separate manual approval
step.

The AI may retry with a fresh governance token **once** when **all** of the
following are true:

- The pre-commit hook blocked a protected governance path.
- The staged diff exactly matches the current authorized route scope, no extra
  file has been staged.
- No unrelated file is included in the index.
- The token was generated by running the approval script against that exact
  staged protected-file set.
- The retry and its reason are recorded in session output. If a session-log
  state writer is available, also append a `stop_event` entry. If the writer
  is unavailable (environment restriction, missing runtime), record the reason
  inline in the commit body and continue - the writer being unavailable is not
  itself a hard stop.

If the staged diff contains **anything extra**, this is a hard stop. Do not
generate a token and retry, surface the over-scope to the user first.

The token must not be generated pre-emptively or reused across route
boundaries.

---

## 5. Hard-Stop Conditions

The following are binary triggers. If any is observed, stop immediately, emit
the banner, and write a `stop_event`. Do not interpret or reason around them.

1. Next action touches a file outside the declared `allowed_files`.
2. Next action touches a repo outside the declared `allowed_repos`.
3. Validation fails after one scoped repair attempt.
4. The staged diff contains files not in the authorized route.
5. An ownership conflict is detected in `ACTIVE_EDIT_OWNERSHIP.md`.
6. A governance file would be changed without a matching authorization token.
7. The route requires a phase (`push`, external API call, spawn sub-agent) that
   was not declared in `allowed_phases`.
8. Governance-token retry is triggered but the staged diff is not exactly the
   authorized scope.

Hard-stop banner:

```text
STOP [reason] | route=[route_name] | needs your decision: [one question]
```

Write a `stop_event` with `resolution: "fired_awaiting_user"` before emitting
the banner. See `failure-recovery-flow.md` for the full hard-stop handling
procedure.

---

## 6. Failure Decision Tree

For recoverable issues inside a route, apply `failure-recovery-flow.md` in full.
The summary relevant to route execution:

| Situation | Action |
|-----------|--------|
| Ownership conflict | HARD STOP |
| Scope exceeds frozen plan | HARD STOP |
| Validation fails, one repair attempted and failed | HARD STOP |
| File/section missing after two searches | `[Gap/Unresolved]`, continue if independent work remains |
| Blocked task, independent task exists | `[SKIPPED]`, continue |
| Recoverable issue (typo, stale heading) | Minimal fix, continue |

See `failure-recovery-flow.md` for the full decision tree and `task_state`
field mappings.

---

## 7. Multi-Agent Policy

Within a route:

- **Default:** single writer, any number of read-only scouts for discovery.
- Read-only scouts may search, read, and report in parallel; they may not stage
  or commit.
- **Scout findings do not expand route scope.** If a scout discovers a file or
  issue outside the declared `allowed_files`, that discovery is reported but
  does not become executable work in the current route. It may be proposed as
  a separate route in the session-close recommendation.
- No parallel write mode within the same worktree.
- Write-capable parallel work requires separate worktrees and explicit user
  authorization not already covered by the route.

See `multi_agent_workflow.md` for the full multi-agent dispatch contract and
`worktree-first-policy.md` for isolation requirements.

---

## 8. Session Close

At the end of any route-based continuous execution session, the AI must report:

1. **Route completed / partial / blocked** - which outcome.
2. **Commits** - list of commit hashes and one-line summaries.
3. **Validation** - pass / fail / skipped-with-reason for each commit.
4. **Skipped / gaps** - tasks marked `[SKIPPED]` or `[Gap/Unresolved]`.
5. **Current blockers** - what would need to be resolved to continue.
6. **Next recommended route** - the smallest logical next step the AI would
   take if authorized. This is a recommendation only; it is not an
   authorization. The user must explicitly authorize the next route before
   the AI begins executing it.

If a hard stop fired during the session, include the `stop_event` reference and
whether it was `resumed_by_user` or `bypassed_by_user`.

Run the `session-close` skill before reporting this summary.

## Relationship to Other Protocols

```text
pre-task-decision-flow.md            -> Is this task authorized? What type? What runtime boundary?
route-based-continuous-execution.md -> How far may the AI advance once authorized?
failure-recovery-flow.md            -> What to do when something fails or is missing?
```

All three must be consistent. If they conflict, the more restrictive rule
applies. Surface the conflict to the user rather than resolving it silently.
